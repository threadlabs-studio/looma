# Build generated workspace exports before Docusaurus in clean CI

## Problem

The protected production-docs workflow installed the Looma workspace and then
ran the Docusaurus build directly. The docs app depends on the workspace
`@threadlabs/looma` facade, but that package tracks only its manifest, README,
license, and assembly map. Its JavaScript, declarations, layout entry, loader,
Vue adapters, editor entries, and CSS files are generated by facade assembly.

A developer checkout often already contains those ignored outputs because the
ordinary build and test commands assemble the facade. That made the direct docs
command appear healthy locally while a fresh GitHub runner failed.

## Symptoms

The production workflow stopped at `Build indexable Candidate docs` with module
resolution errors for:

- `@threadlabs/looma`
- `@threadlabs/looma/layout`
- `@threadlabs/looma/tokens.css`
- `@threadlabs/looma/theme-light.css`
- `@threadlabs/looma/layout.css`
- `@threadlabs/looma/styles.css`

The immutable Candidate-run lookup, exact source checkout, artifact download,
registry-evidence download, and manifest verification had all passed before the
build failed. This ruled out stale release bytes or an incorrect Candidate
binding.

## What Didn't Work

- Re-running the direct Docusaurus command in a clean checkout reproduced the
  same missing-module errors.
- A successful docs build in the long-lived development checkout was not valid
  evidence because ignored facade outputs were already present.
- `pnpm install --frozen-lockfile` correctly linked the workspace package, but
  package linking cannot create the generated files targeted by its export map.

## Solution

Both manual Pages workflows now build the facade after dependency installation
and before Docusaurus:

```yaml
- name: Build Looma facade
  run: pnpm build:facade
```

`pnpm build:facade` builds the core, layout, editor, and Vue inputs and then
assembles and verifies the singleton `@threadlabs/looma` package. The existing
docs command can then resolve every facade entry it imports.

The workflow-policy test records ordering, not merely command presence: it
requires `pnpm build:facade` to appear before the Docusaurus build in both
`.github/workflows/docs-preview.yml` and
`.github/workflows/docs-production.yml`.

## Why This Works

The facade export map points at generated package-local targets such as
`dist/index.js`, `layout/index.js`, and top-level CSS files. A workspace symlink
only exposes what is present in that package directory. Explicit facade assembly
materializes and validates those targets before webpack resolves the docs app's
imports.

The ordering test prevents the same failure from returning if either workflow
is reorganized. Testing both workflows matters because they share the same clean
checkout assumption but have separate YAML definitions and release roles.

## Prevention

- Verify release and documentation workflows from a fresh checkout, not from a
  working directory that may contain ignored build outputs.
- Treat generated workspace exports as explicit build dependencies in every
  isolated job that consumes them.
- Assert workflow ordering when one step produces the files consumed by a later
  step; checking only that both commands exist is insufficient.
- When a package resolves locally but all of its exported subpaths fail in CI,
  compare tracked package files with export-map targets before changing the
  bundler or package manager.
